# 07 — Internationalization (EN / VI / JA / ZH-CN / RO)

Baseline matches the portfolio standard: **English (default), Vietnamese,
Japanese**. v1.2.0 adds **Simplified Chinese (`zh-CN`) and Romanian (`ro`)** —
the two languages the CWS dashboard showed real installs and active users in
after the first three. Two mechanisms with a strict split:

| Layer | Mechanism | Why |
|---|---|---|
| Manifest strings (name, description) | `chrome.i18n` + `_locales/` | Required by CWS for localized store/manifest fields; follows the *browser* UI language. |
| All in-app UI strings | Custom runtime store (`src/lib/i18n/`) | Users must be able to switch language **in Settings**, independent of browser language — `chrome.i18n` cannot do that. |

## 1. `_locales/` (manifest-level only)

```
src/public/_locales/en/messages.json      ← default_locale
src/public/_locales/vi/messages.json
src/public/_locales/ja/messages.json
src/public/_locales/zh_CN/messages.json   ← Chrome's directory name, underscore
src/public/_locales/ro/messages.json
```

```json
{
  "appName":  { "message": "BookmarkMagic" },
  "appDesc":  { "message": "Import, export & edit bookmarks between browsers — offline, no account, no cloud." }
}
```

`wxt.config.ts` manifest: `name: "__MSG_appName__"`,
`description: "__MSG_appDesc__"`, `default_locale: "en"`.
Keep `appName` identical in every locale (brand name is not translated);
`appDesc` is translated and stays ≤ 132 characters (the manifest limit, enforced
by `manifest.test.ts`).

Directory names are **Chrome's**, not BCP 47: `zh_CN`, with an underscore. The
runtime locale id is the BCP 47 tag `zh-CN` (§2). The one place the two are
mapped is `CHROME_LOCALE_DIRS` in `tests/helpers/locales.ts`; `manifest.test.ts`
uses it to fail on a missing `messages.json` and on a `_locales/` directory no
locale owns.

Chrome resolves a manifest string by trying the full UI locale, then its
language, then `default_locale` — so a Traditional Chinese browser (`zh_TW`)
falls back to **English**, never to `zh_CN`. §2's runtime rule deliberately
matches it, so the name in `chrome://extensions` and the UI agree.

## 2. Runtime i18n — `src/lib/i18n/`

```ts
// resolve-locale.ts — the single list of shipped locales
export const LOCALES = ['en', 'vi', 'ja', 'zh-CN', 'ro'] as const;
export type Locale = (typeof LOCALES)[number];
```

`as const` is correct **here** — this is a list of ids, not a dictionary (the
ban below is about dictionaries). Every table keyed by locale is a
`Record<Locale, …>`, so a locale added to `LOCALES` and missing anywhere else is
a compile error rather than a silent English fallback: `dicts` in
`index.svelte.ts`, `TAGS` in `format.ts`. `storage.ts`'s allow-list is
`['auto', ...LOCALES]` and the Settings choices are built from the same array.

```ts
// locales/en.ts  (every other locale mirrors the exact same shape)
import { importTab } from './en-import';
import { errors, warnings } from './en-notices';

const dict = {
  common: { import: 'Import', export: 'Export', edit: 'Edit',
            settings: 'Settings', about: 'About', cancel: 'Cancel', /* … */ },
  import: importTab,                 // en-import.ts: dropHint, mode, stats, progress …
  /* popup, status, export, edit, settings, about, legal … */
  warnings,                          // en-notices.ts
  errors,
};

export default dict;
/** Widened (string, NOT the literal 'Import'); plural branches may add `few` (§5). */
export type Dict = Localized<typeof dict>;
```

```ts
// locales/vi.ts  (ja.ts, zh-CN.ts, ro.ts identical in shape)
import type { Dict } from './en';
import { importTab } from './vi-import';
import { errors, warnings } from './vi-notices';
export default { /* …, */ import: importTab, warnings, errors } satisfies Dict;

// locales/vi-import.ts — each part is checked on its own
export const importTab = { /* … */ } satisfies Dict['import'];
```

**Each locale is three files** (since v1.1.0): `<lang>.ts`, `<lang>-notices.ts`
(`warnings` and `errors`) and `<lang>-import.ts` (the Import tab). `<lang>.ts`
re-assembles them, so the runtime shape and every key path are unchanged — the
split exists only to keep each file under the `10 §1` size limit as codes and
Import strings are added. In the non-English locales the parts are typed
`satisfies Dict['warnings']`, `Dict['errors']` and `Dict['import']`, so a
missing key fails `tsc` in the very file that lacks it. A new string goes in
whichever file holds its branch.

```ts
// index.svelte.ts
const dicts: Record<Locale, Dict> = { en, vi, ja, 'zh-CN': zhCN, ro };
let locale = $state<Locale>('en');                 // hydrated from settings store
export function t(path: string, params?: Record<string, string | number>): string
// resolves dotted path in dicts[locale], falls back to en, interpolates {tokens}
export function setLocale(l: Locale) { locale = l; }  // settings store persists
```

- `en.ts` is the **schema source of truth**; every other locale is typed
  `satisfies Dict` → missing keys fail `tsc` (compile-time completeness check,
  no i18n framework needed).
- ⚠️ **Do not write `as const` on `en.ts`** (or any dictionary). It would make
  `typeof dict` a tree of *string literal* types, so `satisfies Dict` would
  demand `vi.common.import === 'Import'` — every correct translation becomes a
  compile error and the only way to make a locale build is to leave it in
  English.
- `Dict` is `Localized<typeof dict>`: `typeof dict` with every plural branch
  (`{ one, other }`) widened to `{ one, other, few? }`. That optional `few` is
  the only thing it adds — it lets Romanian carry its third form (§5) without
  every other locale writing a dead one. Whether a locale carries `few` is
  checked at runtime, not by the type.
- `Dict` is exported from `locales/en.ts` (a leaf module), **not** from
  `index.svelte.ts`. That module imports every locale and holds runtime
  `$state`, so having a locale import a type back from it forms a cycle that is
  only harmless while the import stays type-only — fragile under
  `verbatimModuleSyntax`.
- Interpolation is `{token}` replacement only. **No string concatenation of
  sentence fragments** — full sentences per key, so word order works in every
  language.
- The document language follows the resolved locale: `<html lang>` is set to the
  locale id (`vi`, `zh-CN`, …). For `zh-CN` that is load-bearing — Chinese and
  Japanese share code points, and `lang` is what makes Chrome pick a Simplified
  Chinese font and glyph forms instead of Japanese ones.

**Initial locale resolution:** saved setting → else map
`chrome.i18n.getUILanguage()` → else `en`. The mapping (`resolveLocale`):

| Browser UI language | Resolves to |
|---|---|
| `vi`, `vi-*` | `vi` |
| `ja`, `ja-*` | `ja` |
| `zh`, `zh-CN`, `zh-SG`, any `zh-Hans*` | `zh-CN` |
| `zh-TW`, `zh-HK`, `zh-MO`, any `zh-Hant*` | **`en`** — matches Chrome's own manifest fallback (§1); the user can still pick 简体中文 by hand |
| `ro`, `ro-*` (incl. `ro-MD`) | `ro` |
| anything else | `en` |

Only whole subtags match: `vic` or `jav` (Javanese) start with `vi`/`ja` but are
not our locales.

## 3. Formatting rules

- Dates in UI: `new Intl.DateTimeFormat(localeTag, { dateStyle:'medium', timeStyle:'short' })`
  with tags `en-US` / `vi-VN` / `ja-JP` / `zh-CN` / `ro-RO`.
- Numbers (counts): `Intl.NumberFormat(localeTag)` — VI and RO use `.`
  thousands, EN, JA and ZH `,`.

Where these live: pure `localeTag` / `formatCount` / `formatDateTime` in
`src/lib/i18n/format.ts` (formatters cached per tag — `StatsCard` alone formats
four counts per paint), plus reactive `num()` / `dateTime()` wrappers in
`index.svelte.ts` that read the current locale. `formatDateTime` returns
`undefined` rather than a string on an unparseable input: `readLegal` coerces a
missing `acceptedAt` to `''`, and `Intl.format(new Date(''))` throws a
`RangeError` *inside a render*, which would blank the About tab.

Three rendered numbers deliberately do **not** go through `num()`, each with a
comment at the site so the next reader does not "finish the job":

| Site | Why |
|---|---|
| `ProgressBar`'s `{n}%` | 0–100; no shipped locale groups two digits, and it is the hottest render path in the app |
| `import.folderName`'s date | this bullet list already pins it to the localized *word* + an **ISO** date; localizing it would rename folders written into the user's browser |
| Export filenames and file contents | locale-independent so a file means the same thing whoever opens it |

ARIA numeric attributes (`aria-level`, `aria-valuenow`) are not display text and
stay raw.
- File names & file contents stay locale-independent (ISO dates, English
  "Imported" folder prefix? **No** — the auto-folder title uses the localized
  word + ISO date, e.g. `Đã nhập 2026-07-03`, key `import.folderName`).
- **Sort A→Z** collates with the UI locale (`Intl.Collator(getLocale())`), so a
  Chinese user's folders sort by pinyin and a Romanian user's put `ș` after `s`.

## 4. Translation workflow & tone

- New strings land in English first — in `en.ts`, `en-notices.ts` or
  `en-import.ts`, whichever holds the branch (PR fails type-check until every
  locale follows).
- **Terminology follows the browser.** Where Chrome (or, for Firefox's root
  names, Firefox) already has a word in that language — bookmark, bookmarks
  bar, folder, import — use the browser's own word, so the extension and the
  browser around it never disagree.
- VI: neutral–friendly register, "bạn"; keep established loanwords
  (bookmark, import/export may stay English in UI where natural — decide per
  string, be consistent; folder = "thư mục").
- JA: です/ます form; katakana loanwords (ブックマーク, インポート,
  エクスポート, フォルダ).
- ZH-CN (Simplified only):
  - Chrome's zh-CN terms: 书签 · 书签栏 · 其他书签 · 移动设备书签 · 文件夹 ·
    导入 · 导出 · 编辑 · 设置 · 关于 · 重复 · 合并 · 替换 · 备份 · 主题.
  - Polite but sparing: 您 where a pronoun is needed. Most strings need none.
  - Full-width punctuation (，。：；？！“”（）). The ellipsis is `…`, as in the
    English source.
  - One half-width space between Han characters and Latin text, numbers or a
    `{token}`: "导出 {n} 个书签", "HTML 文件". No space next to full-width
    punctuation.
  - Measure words with counts: 个书签, 个文件夹, 项 for mixed items.
- RO:
  - Chrome's ro terms: marcaj / marcaje · Bara de marcaje · Alte marcaje ·
    Marcaje mobile · dosar / dosare · a importa / a exporta · setări · despre ·
    copie de rezervă · temă.
  - Polite plural address, as Chrome and Windows use: "Selectați", "Importați",
    "dumneavoastră" where a pronoun is needed.
  - **Comma-below `ș ț Ș Ț` (U+0219/021B/0218/021A), never cedilla `ş ţ`**. They
    are different letters to a search box and a sort. `dictionaries.test.ts`
    fails on a cedilla anywhere in the Romanian files.
  - Quotation marks „…”.
  - Counts take a third plural form (§5): "1 marcaj", "5 marcaje", "20 de
    marcaje".
- **Review policy.** Commit no machine translation unless someone has reviewed
  it. The owner reviews VI. JA, ZH-CN and RO are **best-effort** until a native
  pass, and each file says so in its header: `TODO(review-ja)`,
  `TODO(review-zh)`, `TODO(review-ro)`, with the same marker on any single
  string that is especially uncertain. Native passes are open ⚠️ items
  (`00 §10`), and translation reports arrive through
  `.github/ISSUE_TEMPLATE/translation.yml`.

## 5. Locale-sensitive edge cases

- **Pluralization.** A plural key is an object of CLDR plural forms. Every
  locale carries `{ one, other }`. **Romanian also carries `few`.** The rule is
  mechanical: a locale carries `few` exactly when
  `Intl.PluralRules(tag).resolvedOptions().pluralCategories` includes it.
  - VI, JA and ZH have one grammatical form, so they set `one` and `other` to
    the same string. They must still carry both keys, or the `satisfies Dict`
    shape check that §2 relies on for completeness fails.
  - EN has `one` (1) and `other`.
  - RO has `one` (1), `few` (0, 2–19, and any number ending in 01–19, such as
    101 or 119) and `other` (20–100, 120…). `other` is the form with "de":
    "{n} de marcaje".
  - A count-less noun label — the popup's eyebrows above a big number — is not
    a sentence. There the bare plural noun serves both `few` and `other`
    ("marcaje").

  Implemented as `selectPluralForm(count, tag)` in `i18n/format.ts`. It is
  backed by `Intl.PluralRules` and narrowed to `one`/`few`/`other`; `zero`,
  `two` and `many` fold into `other`, and no shipped locale produces them.
  `tPlural(path, count, params?)` in `index.svelte.ts` supplies `{n}` already
  grouped for the locale, so callers pass a raw count. It falls back from the
  selected form to `other`, then to English.

  `tests/unit/i18n/dictionaries.test.ts` enforces the shape:
  - every plural key carries exactly the forms its locale's rules need, and
    nothing else;
  - `few` is compared against English `other` for interpolation tokens;
  - **every shipped locale's `pluralCategories` ⊆ {one, few, other}**. A future
    locale that needs `two` or `many` (Arabic, Polish, Russian…) fails there
    first, before anyone ships a grammar the helper cannot select.

  The plural keys are **every** `warnings.*` code. That includes the two that
  interpolate no count: `ParseWarning` always carries one, and a uniform shape
  lets `WarningList` call `tPlural` unconditionally instead of keeping a list
  of which codes count things. Beyond those come `import.warnings.title` and,
  since v1.1.0, eighteen more:
  - `popup.bookmarks`/`folders`;
  - `export.start`;
  - `import.start`, `countBookmarks`/`countFolders`, `reused`,
    `cancelledSummary`, `partialCreated`/`partialCleared`;
  - `edit.deleteFolderBody`, `keepFirst`/`keepFirstBody`, `sortBody`,
    `showMore`/`showEarlier` and `duplicateLinks`/`extraCopies`. The duplicate
    summary was one string with two counts, so it read "1 duplicated links · 1
    extra copies".

  Anything else stays a plain string.

  ⚠️ **No non-plural key may be named `one`, `few` or `other`.** The test reads
  any branch holding one of those keys as a plural and fails it unless its keys
  are exactly the plural forms. That is why the Firefox root names are
  `import.rootTitle.{toolbar, unfiled, mobile}`: a third key named `other` made
  the branch a malformed "plural".

- **Language labels are endonyms, identical in every dictionary.** A Japanese
  user hunting for Romanian looks for "Română", not "ルーマニア語".
  `dictionaries.test.ts` asserts `settings.lang` is the same in all of them.
- **Every code needs a message, in every locale.** A code with no key renders
  as its own dotted path (`warnings.INVALID_URL`) and no union type can see it,
  so `dictionaries.test.ts` walks three runtime lists:
  - `PARSE_WARNING_CODES` (eleven since v1.1.0, each a plural under
    `warnings.*`);
  - `BM_PARSE_ERROR_CODES`;
  - since v1.1.0, `BM_BACKUP_ERROR_CODES` (`browser/errors.ts`, now including
    `BACKUP_EXCEEDS_LIMITS`).

  The last two are plain strings under `errors.*`. A new code goes into its
  list, or the test cannot see it. `BmEnvError`'s codes are covered by
  `BM_ENV_ERROR_CODES`.
- Legal Gate: the four legal documents are **English-only** (canonical), with
  a localized one-line note: "The legally binding documents are in English."
- Store listing: EN required; every other locale's listing goes into the CWS
  dashboard's localized fields (copy lives in `store/listing.*.md`, `13 §3`).

## 6. Adding a locale

Written while adding `zh-CN` and `ro`, so the next language is a checklist and
not an investigation. Each step names what fails when it is skipped.

1. **Plural forms first.** Check
   `new Intl.PluralRules(tag).resolvedOptions().pluralCategories`. If it holds
   anything besides `one`, `few` and `other`, stop: `format.ts`, `Localized`
   and the dictionary tests need a new form before any translation can be
   correct. The guard test fails here anyway.
2. `LOCALES` in `resolve-locale.ts`, plus a `resolveLocale` row and its tests.
   `tsc` then demands the `dicts` entry (`index.svelte.ts`) and the `TAGS`
   entry (`format.ts`).
3. Three dictionary files modelled on `ja.ts` / `ja-notices.ts` /
   `ja-import.ts`, with a tone header and the `TODO(review-xx)` marker.
4. The endonym in `settings.lang` of **every** dictionary (the endonym test
   fails otherwise).
5. `src/public/_locales/<chrome dir>/messages.json`. Also add it to
   `CHROME_LOCALE_DIRS` (`tests/helpers/locales.ts`), to `REQUIRED_FILES`
   (`scripts/check-manifest.mjs`) and to that script's test fixture.
6. `store/listing.<chrome dir>.md` plus its row in `store/README.md`.
7. The language dropdown in `.github/ISSUE_TEMPLATE/translation.yml`, and the
   `LANGS` list in `scripts/screenshots.mjs`. Then run the visual sweep
   (`11 §5`) in both themes for overflow and glyphs.
   `tests/unit/i18n/touch-points.test.ts` fails on any of steps 5–7 left out,
   and on a `LANGUAGES` line in a listing or the README that does not name
   every language.
8. This chapter's tone section, `06 §3.4`, `11 §5`, `README.md`, `CHANGELOG.md`.
   A new UI language is a **minor** release (`12 §4`).
